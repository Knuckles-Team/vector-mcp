# Vector MCP Development

Use this skill when changing the `vector-mcp` connector, its documentation, or
its spec-delivery integration. Work from the repository root and read `AGENTS.md`,
the affected module, and the relevant `specs/` status before editing. Keep the
native epistemic-graph backend as the default and route optional vector providers
through the existing provider policy and SDK contracts.

## Rapid delivery: the 5-minute contract

For a small, reviewable change:

1. Identify one requirement or maintenance slice and name the exact files it touches.
2. Reuse the existing action-routed MCP surface, SDK, central pipelines, and package
   conventions. Do not add another vector transport, planner, publisher, or CI
   framework.
3. Keep spec status generated by the canonical pipeline tools. Run the narrowest
   relevant test, then run `pre-commit run --all-files` from the repository root.
4. Review the complete diff, including workflow and package-data changes, and record
   the source revision plus the commands and results used as evidence.
5. Keep credentials, provider endpoints, generated output, caches, and scratch files
   outside the checkout. A Pages claim is complete only after the central reusable
   workflow has run and the exact published `spec-delivery/` source is checked.

### Change boundaries

- Preserve the native epistemic-graph default, action-routed tools, provider policy,
  refusal behavior, and packaged vector ontology and source mappings.
- Keep optional provider imports lazy and resolve credentials through the existing
  runtime configuration and secret-reference paths.
- Extend an existing retrieval or collection operation before adding a new abstraction.
- Use the central Pages workflow and `.config/spec-dashboard.json` for the spec
  dashboard; keep one documentation publisher for this repository.
- Keep the central aggregate hooks in `.pre-commit-config.yaml`; do not copy their
  implementation or create a second CI framework.

### Validation evidence

For code changes, run the narrowest relevant mocked test first and then the repository
hooks. For delivery changes, validate JSON and YAML syntax and inspect the rendered
dashboard inputs before requesting review. Report failures with the command, revision,
and file or line that needs attention; do not hide a failing check behind a skipped
hook.
